# FireRed trainer battle modes in one Emerald engine

`tools/whole_game/single_rom/battle_modes.py:stage_battle_modes(base, donor, staged_output, report_dir)` imports source into an isolated merge after the state transform. No canonical source, shared build tree, ROM or browser was changed.

All ten FireRed trainer mode IDs are audited. Modes0–8 have identical source argument descriptor layouts to Emerald. FireRed early-rival9 collides with Emerald Pyramid9; it is assigned13, preserving all native modes0–12. `include/constants/whole_game_fr_battle_modes.h` supplies the donor constants and is included by native battle_setup constants before script conversion. The source converter must read that staged provider or explicitly override EARLY_RIVAL13.

The exact FireRed early-rival descriptor loads mode, donor trainer ID, rival flags, defeat text, victory text and return script. It clears stale Emerald two-opponent approach state. The source outcome branch preserves VAR_RESULT, win/loss/draw, optional healing, whiteout, defeated-trainer flag and quest-log call. A loss without HEAL_AFTER returns before marking a trainer defeated, as FireRed does. The original rival-loss battle script recalls the opponent, slides in its trainer and displays the saved victory speech before the original FireRed whiteout continuation. Five original loss strings receive fresh IDs381–385, preserving the native message table.

Normal donor victories and VS Seeker rematches avoid Hoenn Match Call side effects. Rematch modes5/7 call original donor helper providers explicitly instead of looking up donor IDs in the Hoenn table. Those providers are required externals, not success/no-op implementations. Namespaced defeated flags remain owned by the state transform's WholeGame_TrainerFlag accessors.

`WholeGame_IsFireRedTutorialBattle()` requires trainer battle type, a real donor trainer ID, mode13 and the original rival flags&3. It does **not** set Emerald BATTLE_TYPE_FIRST_BATTLE. FireRed's Oak controller, initial guaranteed damage/status accuracy and tutorial critical-hit gates differ from Emerald's Birch battle. The separate battle_tutorial provider owns those original source branches; no Birch behavior substitution is claimed.

Four focused tests passed in0.275 seconds: source isolation/mode provider audit, original rival-loss script import, and compiled actual source descriptor/loader/callback execution. The C fixture checks both text pointers and return cursor, stale two-trainer cleanup, twelve flag/outcome combinations, native Pyramid9 preservation donor rematch callbacks, and original money-command zero/nonzero branches. The donor getmoneyreward opcode has a four-byte jump operand, whereas Emerald’s has none; opcode0xF9 imports the actual FireRed handler while native0x5D remains unchanged. Loss only computes/buffers prize money; the travel whiteout task performs the deduction once. A failed intermediate source-pin tuple edit is retained in the transcript and was corrected before the passing run. No cartridge battle, full build or actual story continuation has run. No comparable earlier implementation baseline exists. The ledger records source pins and explicit remaining provider/qualification gaps.

Safari battle core is a separate world_services responsibility and is not certified by this trainer parser stage.

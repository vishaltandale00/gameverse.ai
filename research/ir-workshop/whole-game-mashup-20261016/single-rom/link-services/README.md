# FireRed lobby services with native shared multiplayer

`stage_link_services(base, donor, out, report_dir)` patches an isolated staged Emerald tree. Original decompilations are read-only; repeated application and canonical output paths are rejected. The stage provides all 27 link-multiplayer registry roots and `WonderNews_GetRewardInfo` (including dormant source entries).

Emerald is the authoritative multiplayer engine: its advertised `gGameVersion`, RFU/link task graph, Union Room, colosseum/trade facilities, multiplayer minigames, records, trainer-card and Mystery Gift metadata are shared. Donor lobby scripts enter those native services and preserve their saved dynamic return warp. Bindings are explicit capability choices; identical root bodies alone do not prove callback equivalence. The ledger pins both source definitions, complete native defining translation units, direct calls/state references and numeric cable-room mode/return-warp ABI constants. No network success or failure is fabricated. External cartridge interoperability and donor-lobby return locations still require linked/runtime qualification.

The exact source FireRed wireless detection retains the actual RFU reset/check-ID, ignore-error setting, quest-log playback guard and original cleanup. Its Union Room entry resets the source name buffer before the original playback guard and then invokes the complete native allocation/task service. FireRed revision 0/1 source behavior is selected; Switch revision 10's original networking stub is excluded.

All nine original FireRed in-game trade records, personalities, IVs, species requests/offers, held items, OT names/IDs, contest conditions and mail words are imported from the original source. The original donor construction/mail functions populate the shared native party/enemy/trade-mail buffers. Native trade animation, post-evolution strings and completion use the same regional table; native capture/evolution data remain authoritative. Help disable and save-help-context behavior call the actual utility_services providers, not empty adapters.

Wonder News retains the original reward policy with the donor Mystery Gift enable flag; the Emerald source's different Mystery Event flag is not substituted. Its actual native metadata/cooldown bank is shared and the original field-step hook restored in Kanto. Runtime tests execute source functions through five claims, fourth-send big reward, disabled/invalid gates, 499 steps without reset and the reset at step 500.

External received Mystery Event/Mystery Gift RAM bytecode remains owned by native Emerald's advertised protocol and original raw special-index table. The original Mystery Event version mask rejects properly tagged FireRed-only events. Mystery Gift accepts an opaque script buffer without bytecode-language provenance, so arbitrary raw FireRed payloads masquerading as native cannot be distinguished; they are unsupported. This does not establish compatibility with raw FireRed RAM scripts, and no bytecode translation or registry compaction is claimed. `MEScrCmd_runscript` and `MEScrCmd_initramscript` remain native source dispatch/storage.

## Evidence and cost

Three focused tests pass in 1.148 seconds. Seven complete affected C translation units pass actual agbcc and ARM assembly in 1.962 seconds including source staging/setup; the report pins sources, commands, objects and timings. Retained ELF objects and symbol lists are under `local/re/single-rom/link-services-arm-v1`. No full ROM build or linked/runtime qualification was run by this stage.

A repeated per-symbol source-filter scan was replaced with one compiled token-pattern scan. The same seven-TU harness measured 6.130 seconds before and 1.962 seconds after on this machine/context. These are representative development runs, not a latency budget; the latter source also contains the final Help adapter wiring. Queue, final link and gameplay timings are unavailable.

Run `verify_arm.py --context <retained configured source> --report <path>` to repeat only these seven translation units. The configured input and canonical graphics are linked read-only into private temporary output; no make/full-build command is invoked. Stage after utility_services to satisfy the actual Help System definitions; generation remains fail-closed with explicit missing providers if they are absent.

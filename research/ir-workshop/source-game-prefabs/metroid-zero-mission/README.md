# Metroid Zero Mission source-game prefab phases

`delivery.json` maps nine source gameplay responsibilities and names specific missing producers, consumers and services. `prefab-allowlist.json` exposes independently valid assemblies for existing published packages. These are incremental source phases, not a generated game or a whole-player/combat claim.

Two ready prefab families use actual `Composer` and existing automatic L1:

- **Directional acceleration:** retained player direction and signed velocity enter the source acceleration/saturation helper. The host must supply the eligible pose/input branch. No position integration, terrain, jump, room or camera implementation is supplied. Acceleration4/cap128 are explicitly synthetic editable example settings; original callers load tuning from source RAM.
- **Protected hit response:** one enemy module with source minimum2/minimum3 variants and a separately callable next-eligible reaction phase. Its packed byte preserves the high marker and lower seven-bit countdown. The same enemy HP/freeze/palette state persists through calls. Guard selection and scheduler eligibility remain source/host obligations. The two variants are not two cards. The previously completed accepted-damage core is referenced rather than copied; combining modules must bind the same canonical enemy state.

`build_phases.py` writes the three actual assembly graphs and validation receipts, emits two cores solely through package lowering and Composer, and performs narrow compiled host assertions for the new shared-state wiring. The measured script took0.266080667seconds, including nested graph validation and host compile/assertion stages. It generated no ROM, reran no native campaign and makes no latency speedup claim. Existing original-function native receipts are reused. Queue, full interactive elapsed and a comparable before/after baseline are unavailable.

Acquisition→persistent event readback is the next candidate. The original acquisition root already updates the source event bank, but published event/acquisition collection meanings and operation-dependent return semantics need an owner-controlled metadata overlay before assembling their shared bank. `progression-semantic-proposal.json` pins the exact own-ROM source evidence. No private fake bank or authored event algorithm is substituted.

The source C files are semantic evidence only. Automatic behavior input remains the previously exported HighFunction/L1. See `source-evidence.json`, existing native package receipts, actual graph validation receipts, `phase-verification.json` and `delivery-verification.json` for precise proof limits.

# Presentation transfer experiment, 2026-10-16

Three bounded offline probes rendered original recovered/source assets successfully. They establish reusable pieces of a presentation interface, not a playable mashup or a complete visual-style transfer. No prior Sonic×Metroid game was rebuilt, run, restored or published. Its retained low-level MZM asset extraction evidence was reused only as an independent asset closure. No ROM/L0/copyright notice was altered; generated copyrighted pixels remain in ignored `local/`.

## Compatibility families and explicit incompatibilities

Side-view pixel families (1–3,10–11,16–19,26–30,33) share screen axes and may reuse packing, pivot and camera conversion blocks. That does not make their characters physically interchangeable: broad Wario, round Kirby, tall Samus/Prince have different silhouette/attack extent and state obligations. Similar source-backed Emerald/FireRed walkers provide the strongest tested near-family pairing. Overhead orthogonal scenes (5,7,8,12–13,25; field source for 21–24) can share grid/foot-depth primitives but GTA vehicles introduce heading and scale. Oblique/isometric families (6,9,14) require explicit elevation/projector/depth ordering; they cannot consume orthogonal map coordinates without a transform. Kart/NFS/Driv3r perspective families (4,15,20) require road/world projectors and orientation-dependent images or geometry, not a palette swap. Tekken shares a side-facing encounter plane but large articulated attack poses and perspective floor make its obligations substantially different. World-map/portrait/menu art is a separate presentation role, never a substitute for unseen gameplay assets.

## Proposed reusable presentation interface

This is a local experiment contract proposal, not an added mandatory host API or a complete IR implementation. Keep simulation, art and runtime services separately versioned.

| Block | Minimum reusable inputs and outputs | Must validate / keep distinct |
|---|---|---|
| Asset closure | Immutable source identity; indexed pixels/tiles; palette banks; bpp/packing/stride; metasprite pieces; local offsets/sizes/flips; transparency; original notices. | Existing MZM 4bpp closure proves this; never identify an art object by bare tile ID across games. Missing palette or secondary tiles is visible failure. |
| Pose/animation binding | Semantic pose/facing plus elapsed simulation ticks/event edges → source clip/frame/local transform; tick rate; loop/end/reset/hold semantics. | Source clip names/frame IDs are not cross-game semantics. MZM64tick loop vs32tick Pokémon gait differs. Preserve source duration/events unless change is deliberately authored. |
| Spatial binding | Simulation position/unit/frame, visual pivot, feet/weapon emitters, collider overlays → draw anchor. | Pixels vs quarter/1⁄256px; y-down; visual center vs feet; scale mismatch must not silently alter collision. Foot pivot in probe2 is authored only. |
| Projector/camera | World+elevation→screen; camera offset/zoom/rotation; viewport; deadzone/lead/lag/clamp; background layer scroll factors. | Ordinary screen subtraction is insufficient for isometric or perspective worlds. No camera/parallax timing validated here. |
| Layer/material binding | Stable semantic floor/wall/roof/door IDs → per-style metatile/mesh refs, foreground priority/occlusion, palette, animated-material event. | Metatile attr/layer mode and game collision behavior remain authoritative simulation inputs. Probe3 deliberately does not claim universal64-ID equivalence. |
| Effects/UI | Event→effect clip/anchor/lifetime; state→text/icon/bar; font metrics/safe areas; priority/blend/flash/visibility. | Source-readable life/ammo/card HUD has different semantics; changing art must retain cues and label actual source/adapter coverage. |
| Renderer/runtime adapter | Draw lists→native OAM/VRAM or canvas; declared capacities, palette ownership and restoration, priority/blend support. | Existing native bridge depends on specific Sonic OAM/VRAM host-call addresses and camera RAM, not a portable renderer. A renderer can be authored around recovered art without claiming recovered engine code. |

2. Tile transfer needs semantic mapping (ground/wall/roof/door/water), not byte-slot sharing. Read `data/layouts`, `data/tilesets/*/metatiles.bin`, `metatile_attributes.bin`, palettes and tiles together; recover map-block behavior/collision/layer mode and compare one actual bounded room. A correspondence table can admit only supported material roles. This unlocks Emerald/FireRed room style experiments; no complete map converter exists here.
3. MZM next step is independent controller-state → animation-event parity, using `mzm_ripper.h` and retained extraction receipt. Asset output is already available; no more ROM extraction needed. Do not resurrect the retired game to test this. Native host support additionally needs explicit alloc/lease/release and renderer address relocation instead of old hardcoded Sonic RAM/ROM calls.
4. For other games with no semantically typed art closure, use the existing bounded observe→decode path, not broad ROM scans: `tools/re/capture/run_captures.py --ids <one-id> --jobs 1 --timeout 30 --asset-trace-limit 64 --asset-snapshot-max-bytes 65536`, then `tools/re/assets/decode_loaded.py` with pinned capture root. Follow a visible sprite's source read/OAM construction and pin gfx/palette/clip pointers before exporting. Existing3-game pilot can seed Crash/MZM/Emerald, no new capture required until a specific missing role is selected.

Shared tooling opportunity is a source-pinned asset-closure inspector, one generic indexed/metasprite/clip previewer, semantic pose/material binder and collider/camera overlay. Reuse existing capture/decode/session observability; no extra CI stage, dependency, matrix or central orchestrator was added. A real portable renderer prefab, projection/camera IR, animation-event IR and per-source palette/material maps remain missing.

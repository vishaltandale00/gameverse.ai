# Generic mechanic binding contracts

This edition derives interfaces from the current qualified package registry without changing its proofs or the historical extraction snapshot. The separate `editions/112-packages-4970305d85556c68/` directory preserves the earlier 112-package edition; current counts and exact identities live in `index.json` and `validation.json`. `index.json` links every public port to its actual L1 field, storage/direction and evidenced quantity/unit/frame. Parameters, extracted configurations, collections, source domains, owner labels, source aliases, lifecycle/order, services and limitations remain visible. Private state stays per instance; owner labels alone never establish shared backing or aliases.

`relations` are generic **candidates** formed by exact storage/quantity/unit/frame/signed-encoding equality and output-to-input direction. They are not a game-pair whitelist, automatic bindings or proven compatibility. Different units are not silently converted. Domain, packed-view, shared-owner, clock/order and service obligations remain unresolved until explicitly addressed. Actual Composer validation of an exact graph returns `binding_valid_obligations_unproven`; this is structural lowering evidence, not native composed parity or source scheduler closure.

Source-contract references resolve to a shared `sourceContracts` map. Each reference records its expected/current hash and pin status; missing or changed references remain explicit. Inline source metadata is retained too. The current backend accepts symbolic package invocations and no external runtime services; this edition does not invent adapters for unresolved world/audio/display clocks.

Run `python3 ontology/composition-contracts/build.py` to regenerate the index and `validation.json`. The stdlib check reads existing package/L1/receipt identities and validates public-port metadata against actual L1 fields/effects. It performs no extraction, native simulation, compilation or ROM generation. Its measured duration and exact input/output hashes are retained; there is no comparable prior edition baseline.

`examples/mzm-reaction-transfer.json` is an editable two-component binding graph. It shares the exact packed reaction byte between `mzm.combat.minimum_reaction2` and `mzm.combat.reaction_tick`; other tick inputs use their exact sourced roles. The source minimum helper belongs to a hit guard, while reaction ticking belongs to the **next eligible enemy scheduler invocation**. The graph's explicit invocation order is an assembly design, not proof that the original scheduler has been recovered. The packed marker/countdown byte is shared intact; no fields are reinterpreted as wall time. Source HP/freeze/palette inputs are explicit graph initialization choices. The example is not a game or preset generator.

Validate an exact graph with `python3 tools/behavior_ir/assembly.py --request ontology/composition-contracts/examples/mzm-reaction-transfer.json --out ontology/composition-contracts/examples/mzm-reaction-transfer.validation.json`. This invokes the real Composer's binding/type/domain/lowering path in memory, without generating a ROM. Validation status and all warnings must remain visible.

`patterns.json` contains advanced internal binding motifs. They are not primary game-system blueprints: a timed gate, secure-record transform or two reaction helpers does not supply a coherent player-facing system. Player-facing plans must expose their source subsystem's responsibilities, persistent actor/world identity, lifecycle, dependencies and missing closure. The expanded traversal, damage/reaction and learned-ability descriptors under `research/ir-workshop/game-system-assembly-20261016/` keep these boundaries visible. Their source recovery, individual native receipts, portable binding admission and any compiled host assertions are separate kinds of evidence; none by itself establishes a complete playable system.

`gameSystemAssemblies` retains those lifecycle descriptors with exact source and artifact pins. `capabilityBundlePackets` retains the source-owned Mario, movement, and combat/progression facets. A facet is a role view over its declared `moduleId` and canonical state, rather than a request for another actor or another recovered subsystem. Automatic package references resolve against the current catalog; native-host package references remain separately identified in the original facts. Required support, source-only consumers, service obligations and missing closure remain part of each bundle. Component package equality and a receipt's whole-catalog identity are reported separately.

# Continuous automatic extraction policy

The objective is the local ROM collection's usable movement, combat and progression ontology, plus qualified multi-game compositions. A checkpoint, successful export or per-batch resource cap is not completion.

The optional local `pipeline.py` queue records each ROM's independent export, candidate, native-qualified, semantic-port-ready and mechanics-closure-ready counts. Mario is included following the user's latest instruction. `depth.py` closes prioritized behavior dependencies and only publishes explicitly qualified mechanics. Unresolved pointers/services/ABIs stay actionable pending work, not invented components. After each bounded invocation, continue another ready item or compiler/dependency repair; preserve the queue and report a precise continuation handoff if execution must yield.

New usable packages must update `ontology/executable-components` and the existing local site's component catalog without changing Vishal's base navigation. Repeated bounded composition trials must select different compatible game components, compile new ROMs, run actual native input scenarios and retain hashes, screenshots/video, failures and incompatibility diagnostics. Authored world/runtime behavior remains distinguishable from ROM extraction. Never work around a failed composition by hand-patching behavior C.

Default discovery: one JVM,800 prioritized candidate functions,45s export/45s static lift per ROM,75s hard export-process timeout,15min per invocation. Default depth: at most8 native targets per batch,16,384 vectors each,30s per native stage. These are configurable limits, not permission for unlimited model spending. No paid API calls are needed by this pipeline. Reuse pinned artifacts and qualifications when their semantic/compiler dependencies are unchanged; don't rerun a broad native matrix merely because another ROM exported.

No browser game testing. Do not retry a blocked remote push independently. Source-only local checkpoints may be committed on the user's branch while the coordinating agent handles publication.

Active depth priority is comprehensive Mario mechanics (SMA1/2/4, followed by the separate bundled engines, Mario & Luigi and Mario Kart families). Keep all33 ROMs pending; do not leave a game because one lane became usable. `research/automatic-ir/mario-mechanic-coverage.json` is owned/refined by the mechanics evidence agent. Do not overwrite its game-specific obligations with a generic platformer checklist.

The next compiler blocker is intentional shared actor/world storage: SMA4 actor r0 is a world-pool view with slot handle, not independent memory. Preserve accessed-window alias relations, explicit field/index domains and real r2 call arguments. Broad padded context extents are not proof of separation. Unsupported cases remain pending, never copied into an apparently working but incorrect prefab.

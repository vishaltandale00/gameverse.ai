# Native improvement API v1

Implemented seam for Vishal's R3 voice agent and Shishir's native worker. This additive local transport implements a bounded subset of [PARALLEL_DEVELOPMENT.md](PARALLEL_DEVELOPMENT.md); it does not close slice 3. Vishal owns base/subgame hosting, navigation, saves, acceptance and activation. The worker only returns isolated candidate artifacts and evidence.

Run `node scripts/serve-improvement.mjs` (Node >=22, Python 3) for the API alone on localhost:4175. The minimal handoff does not require the frontend. Native build requests need no model credential. Native improvement requests use the existing configured S1/S2 providers and local credential references; credentials never enter the request envelope or published source. `PORT` and `IMPROVEMENT_TIMEOUT_MS` (1,000–300,000; default 90,000) configure transport/outer worker bounds. Recipe-specific bounds remain in their registered loop requests. For a registered iteration chunk, the outer watchdog allows at least its configured wall limit plus 15 seconds for cleanup; the voice client does not select resource budgets. Only one job runs; busy requests receive 409 rather than entering an unbounded queue. Native builds need ARM-capable Clang as `cc` plus GNU ARM binutils (`arm-none-eabi-ld`, `arm-none-eabi-objcopy`, `arm-none-eabi-nm`) on PATH. Native bot experiments and Double-XP native qualification additionally need the existing mGBA session bridge/toolchain; its standard setup is in `tools/re/session/README.md`.

Input ROMs are user-supplied local files and never distributed. Registered request JSON uses repository-relative paths under `local/roms/`; capability discovery reports missing or stale input paths. Provision the exact named local ROM inside the checkout; digest validation remains mandatory. A matching descriptor inventory alone does not establish an executable backend. Backend admission independently checks source/plan/package/qualification pins. When `contracts/improvement-provider-pack.json` is installed, capability admission verifies the reviewed per-recipe runtime readset and its recipe digest; historical capture references are not runtime prerequisites. Historical provenance warnings remain separate. The manifest digest contributes to `loop_version`. Without that manifest, development fixtures use recursive declared pins. `installed` reports recursively declared file-pin availability, not a guarantee that its toolchain, undeclared dependencies or runtime checks pass. A fresh checkout without private inputs can serve capabilities and return a visible missing-input error.

| Method/path | Result |
| --- | --- |
| GET `/api/improvement/capabilities` | Versioned adapter, loop code revision, registered recipe requests/digests, missing pinned inputs and supported capabilities |
| POST `/api/improvement/runs` | 202 after durable request receipt and native worker dispatch; retry identical ID/input to recover same job |
| GET `/api/improvement/runs/{uuid}` | Durable run status, input pins, live engine stage/usage observations, checkpoint availability, backend evidence and timing |
| POST `/api/improvement/runs/{uuid}/continue` | New UUID/pinned lineage starts another registered resource chunk from an admissible checkpoint |
| GET `/api/improvement/runs/{uuid}/artifacts/iteration` | Current engine report, digest checked against the status snapshot |
| DELETE `/api/improvement/runs/{uuid}` | Request cancellation of current worker/process group; poll for retained terminal status |
| GET `/api/improvement/runs/{uuid}/artifacts/result` | Retained backend result JSON |
| GET `/api/improvement/runs/{uuid}/artifacts/rom` | Candidate standalone native `.gba`, digest checked on download |

Loopback Host is required, supplied Origin must match it and cross-site requests fail. Non-browser local agents may omit Origin. This uses the current app's local-origin trust model; remote authenticated hosting is not implemented. Receipts persist under ignored `local-data/improvement-runs/`. They are local durable files, not a distributed multi-server queue. A restart marks an orphan running receipt interrupted and never replays work silently. Cancellation or failure cannot activate a candidate or overwrite player progress. Same ID with different input returns 409, missing/stale inputs return 422/409, unsupported operation/recipe/target returns 422. Error bodies contain `{error:{code,message}}`.

The existing `native-mod` operation retains `aria-double-xp` (`mod-rom`) and `aria-soulstride` (`build-mod`). A separate `aria-soulstride-controlled-lunge` recipe is an explicit legal 1px lunge baseline with a reviewed 3px repair variant; it does not replace the original Soulstride baseline. Double-XP repeats the explicitly bounded 14,720-vector comparison and original/parity/modified 6,400-frame corridor; it is suitable for a deliberate qualification request, not automatic transcription or routine CI. Soulstride builds a substantial connected bone-birth/lunge, moving-defeat MP refund and soul progression candidate, without running model gameplay or establishing objective completion when submitted as `native-mod`. Both preserve the original cartridge outside explicit native hooks; neither reconstructs the full game into IR. Reconstruction operations, arbitrary game generation, arbitrary natural-language edits, FireRed modification, arbitrary code repair, migration and host activation are unsupported. The registered native-improve operation may select an exact reviewed repair variant through evidence-linked model diagnosis; it cannot execute generated prose or arbitrary edits. There is no fallback demo generator.

`native-improve` uses `iteration_profiles` from capabilities and requires `plan.profile_id` plus the exact `profile_sha256`. The registered `aria-soulstride-iteration` profile targets `aria-soulstride-controlled-lunge` and invokes the existing preparation → native build → native S1/S2 experiment → diagnosis → reviewed repair → re-admission/build loop. The profile owns attempts, model calls, native frames, wall time, optional cost budget and S1 confidence/margin policy. Its declared S1/S2 model/provider identities are pinned by the profile, enforced by the existing bot and retained with effective endpoint/model bindings in experiment evidence; local credential files are configured only through `GAMEVERSE_SID_ENV_FILE`. The existing S1 decision gate determines when S2 runs; API code provides no bypass. Prepared inputs retain current mechanism/model-policy/config pins. A successful process exit and available ROM do not prove that the observed objective passed.

For `native-improve`, status retains `engine_status`, `experiment_outcome`, `qualification`, `usage`, `usage_complete`, `checkpoint_available`, `report_sha256` and actual stage/attempt observations in `progress`. The final result retains decisions, observations, diagnosis and repair evidence from the engine. `completed` can mean an available candidate with diagnostics or exhausted resources; inspect the separate native objective qualification. Reports and emulator/model checkpoints remain private local run data. Unknown interrupted-stage usage blocks continuation instead of replaying potentially billed work.

A continuation is a new request ID at `POST /runs/{prior_id}/continue`, with the same frozen target, environment, profile identity/hash and loop version, plus current recipe pins and `prior_report_sha256` from prior status. The API requires that the loop version still equals both the prior run and current capabilities. A changed engine revision requires a new initial run; old reports are never repinned to pass continuation checks. The worker validates the exact artifact, state, model context, known usage and environment/adapter compatibility. Each chunk uses the unchanged registered policy and records explicit lineage and per-chunk usage; no hidden unbounded run or client-selected budget is introduced. Repeating the same submission ID is idempotent; continuation creates a distinct job. Original terminal receipts stay unchanged. The worker may reuse an exact pinned native build; API downloads retain a verified run-local artifact copy. Cancellation/unknown interruption cannot resume automatically.

The voice agent reviews the captured transcript, freezes the game/host target, chooses a supported structured plan, and submits it. Text is retained intent/context; it is never silently treated as executable code. If text cannot map to a supported recipe, the agent must surface unsupported/needs-plan locally instead of pretending the request ran. No manual IR assembly is required for these registered recipes. Existing `/api/voice/requests` receipts can be linked with `voice_request_id`; the server checks the frozen transcript plus `context.gameId`, `role`, `gameVersion`, `artifactSha256` and rejects cancellation or retargeting. Submitting voice text alone does not enqueue an improvement.

Example agent integration (the same values fit the POST JSON schema):

```js
import { submitImprovement } from './scripts/improvement-client.mjs';
const job = await submitImprovement({
  server: 'http://127.0.0.1:4175',
  recipeId: 'aria-soulstride',
  intent: reviewedTranscript,
  requestId: durableRequestUuid, // retain this AND job.request for network retries
  target: {
    role: 'subgame', game_id: 'castlevania-aria-of-sorrow',
    game_version: capturedGameVersion, artifact_sha256: capturedArtifactSha256,
    base_game_version: capturedBaseVersion, base_artifact_sha256: capturedBaseSha256,
  },
  environment: { version: environmentHarnessVersion, config_sha256: environmentConfigSha256 },
  // voiceRequestId: previouslySavedVoiceReceiptId,
});
const run = await job.status(); // poll while running; download run.artifacts.rom only when present
// For the registered full native loop, use:
// operation: 'native-improve', recipeId: 'aria-soulstride-controlled-lunge',
// profileId: 'aria-soulstride-iteration'
// Continue an eligible terminal chunk with continueImprovement({server, priorRunId}).
```

The client fetches capabilities and sends `schema: gameverse.improvement-request/1`, operation `native-mod` or `native-improve`, exact `loop_version` and `plan: {recipe_id, request_sha256}`. Captured baseline ROM hash must match the selected recipe. Game/host/environment version pins are supplied by the environment and recorded as caller assertions; this API cannot check Vishal's accepted baseline remotely. `loop_version` fingerprints the adapter and its listed native dispatch implementation files; it is not a complete toolchain lock. Exact recipe refs, native source/package/build locks, toolchain/platform/source commit and timing are retained by the existing backend result. Host activation must recheck its own expected baseline and compatibility; `completed` means the registered backend produced its scoped result and a digest-verified candidate, not accepted/activated or fully qualified game.

Run quality has independent `scope`, `coverage`, `witnesses`, `gaps`, `save_compatibility` and `reconstruction_qc`. A missing independent `gameverse.reconstruction-qc/1` receipt is reported unavailable. `whole_game_equivalent` remains null. Native-build/ABI preservation, bounded observed behavior and full-game equivalence are different claims. Stages come from existing runner reports and remain nested within backend/worker totals. For native improvement, the legacy `timings.simulation_s` field contains the whole experiment stage, including native play and embedded provider calls; it is composite experiment wall time, not pure emulator execution. `evaluation_s` covers diagnosis. Use the finer native action/policy/provider timings retained by the bot for those individual costs and do not add their nested intervals to the composite again. Queue and unsupported stages are null, never invented zero. Failed/cancelled attempts retain receipts; diagnostics from a killed subprocess may be partial.

Validation evidence: [native API smoke](../research/requests/improvement-api-20261016/smoke.json) and [HTTP route smoke](../research/requests/improvement-api-20261016/http-smoke.json) records actual Soulstride native build and Double-XP native qualification. Focused tests: `node --test tests/improvement-api.test.js`; no CI job, new dependency or qualification campaign is added. There was no prior API transport baseline; measured native backend vs wrapper times from the same dispatch are nested overhead observations, not a controlled before/after speedup claim.

For an isolated checkout, follow [the provider bootstrap and validation guide](IMPROVEMENT_HANDOFF.md). Provider input availability and successful native toolchain execution are separate checks.

The `native-campaign` operation delegates to the existing finite `tools.prefab_pipeline.campaign` controller. It automatically chains exact checkpointed iteration chunks until the observed scenario goal, cooperative cancellation or cumulative caps. A chunk boundary no longer requires another voice/user command. Existing `native-mod` and explicit `native-improve` requests retain their behavior.

The registered `sonic-metroid-coast-campaign` recipe and `sonic-coast-prefix-iteration` profile target the existing native Sonic/MZM artifact `50757987593917bddafe6b32c3355cb9af32d899468850af69115bad59f3d855`, game ID `sonic-metroid-signal-descent`. Its source ROM pin is recorded separately. The source-observation DAG covers earliest Coast with no upgrades → coastal gear/locks → second coastal act → high jump/speed → Factory entry. Stage transitions support the stated first-boss/capsule route; they do not independently prove boss-defeat or switch causality without corresponding native callback evidence. This is a substantive section objective in the existing game, not a new game or full-game completion.

A campaign adds a versioned loop-owned configuration input, separate from voice intent:

```js
const loopConfig = {
  schema: 'prefab-campaign/1', config_version: approvedMeasuredPolicyVersion,
  limits: approvedFiniteLimits, // chunks, repairs, model_calls, native_frames, wall_seconds, cost_usd:null
};
const job = await submitImprovement({
  server, operation: 'native-campaign', recipeId: 'sonic-metroid-coast-campaign',
  profileId: 'sonic-coast-prefix-iteration', intent, target, environment,
  loopConfig,
  // Optional exact retained API prefix, only after its usage/evidence is inspected:
  // adoptFrom: {request_id: prefix.request_id, report_sha256: prefix.report_sha256},
});
```

The client hashes canonical JSON for `plan.loop_config_sha256`. The server rejects unknown loop-config fields, paths, missing/nonfinite caps and unsupported enforceable dollar claims before dispatch. Resource choices belong to the loop owner/configuration, never inferred from transcript text. `campaign_policy.hard_ceilings` are operator guards, not default work allocations or measured latency budgets. Operators configure them with `IMPROVEMENT_CAMPAIGN_MAX_CHUNKS`, `_REPAIRS`, `_MODEL_CALLS`, `_NATIVE_FRAMES` and `_WALL_SECONDS`. No work runs without explicit finite loop-config limits. Larger cumulative policies should follow measured prefix evidence and authorization; a policy input can be changed for a new campaign without changing executable runtime pins.

`plan.adopt_from` accepts an API run ID plus report hash, never a client filesystem path. The prefix must be the exact registered request, target, profile and unchanged runtime with known usage/checkpoint. Its engine request ID and report bytes remain unchanged. The existing controller charges retained prefix calls, frames, repairs, chunk count and execution time exactly once against campaign caps; adoption does not reset usage or manufacture progress. New API job IDs remain separate from the retained engine request identity.

Campaign status exposes actual controller `chunks`, cumulative `usage`, qualification and report digest. When present, `campaign_progress` reports the latest run-local child checkpoint's source-scenario state; unavailable observations remain null. `GET /runs/{id}/artifacts/campaign` serves the digest-checked controller report. Artifact downloads remain run-scoped. `partial` means a finite cap was reached, not that the section objective passed. The report's active time, elapsed time including resume downtime, retained prefix time and nested chunk timings are separate; do not add nested provider/native times to their parent stages.

For campaigns, `DELETE /runs/{id}` writes the controller's cooperative cancellation sentinel, checked at registered stage boundaries. An in-flight stage may finish before cancellation is recorded. The outer watchdog can force-stop an overrun, leaving usage unknown and unavailable for automatic replay. `POST /runs/{id}/resume` requires `loop_version` equal to both the original job and current capabilities plus `campaign_report_sha256`. It resumes the same immutable input/config and remaining cumulative caps, not a new allocation. The controller reconciles pending receipts before any new spend and fails closed on unknown in-flight usage. Remove/recreate work only through explicit new requests; successful/exhausted/blocked terminal campaigns cannot reset their budgets through resume. The example client exports `resumeCampaign({server, requestId})` for this operation. No additional dependency or CI job is introduced.

New campaign profiles explicitly opt into `version_basis: "recipe-readset/1"`. Select their `iteration_profiles[].loop_version`, not the legacy top-level `capabilities.loop_version`, and send the same `version_basis` in the request. The example client chooses this automatically. The token binds the selected recipe registration/request, selected profile bytes and inputs, actual selected runtime-readset files, and shared transport/controller/core code. It excludes unrelated recipe/profile rows and the complete mutable provider-manifest/registry file bytes. Adding an RPG provider record therefore leaves an unchanged Sonic profile token stable; changing shared executable code or that Sonic readset changes its token and blocks stale continuation. Source/runtime closure validation still checks every selected file pin.

Data-only registrations live in `contracts/improvement-profile-registry.json`; only the selected registration records contribute to the new authority. A `gameverse.runtime-readset/1` receipt lists sorted repository-relative paths and actual SHA-256 values. Whole-manifest hashes remain historical provenance for this basis, not compatibility guards. Existing Aria profiles and retained historical jobs retain their original global-version semantics; the server does not silently reinterpret old receipts under the new basis.

A data registration may declare `operations: ["native-improve", "native-campaign"]` with a `native-artifact-traversal-request/1` provider request. This binds an existing original/candidate artifact plus its ELF/save/profile/quality source pins; it is not a modification request. The API rejects `native-mod` for traversal-only registrations. An `artifact-reference` stage records validation/reuse, leaves `build_s` unavailable, and cannot claim a compiler build or changed mechanic. Resource-limited original-baseline traversal is reported `partial` with `artifact_status: "artifact-reused"` and `quality.kind: "artifact-traversal-only"`; game/modification quality remains unknown until its separate evidence exists. This permits the existing RPG bot to use the same finite campaign transport without repackaging original-game play as an improvement.

### Public reference fixture and setup visibility

Capabilities now expose `availability`, `request_template`, `required_context` and `result_routes` on registered native recipes/profiles. `installed` means declared content pins were found; it does not qualify the toolchain, game boot or model service. Native availability therefore stays `setup-required` or `original-required`, with `execution_ready:false` and safe setup instructions. Exported native templates require actual base/game/environment context; the API does not invent those versions.

`fixtures[]` separately describes an executable public authored reference. Copy its exact `request_template`, replace `request_id` with a UUID, and POST it to `/api/improvement/runs`. The outer operation is `reference-fixture`; the adapter invokes the fixed `gameverse.reference-fixture-request/1` executor with inner operation `engine-demonstration` and limits `max_actions:32,max_wall_s:5,max_repairs:0`. Both configuration and the six-file executor closure are pinned. This runs the existing Playtester/GridAdapter/FrontierPolicy on tracked key-door data and replays its action log in a fresh adapter: nine engine actions plus nine replay actions, zero model calls and zero repairs. It requires Python 3 and the tracked fixture files, with no original game inputs or provider credentials. This is authored grid engine evidence, not GBA generation, arbitrary game modification, IR recovery or automated repair.

Poll the usual run URL and follow the retained `artifacts.result` JSON link. Public fixture results expose actual observations/actions, tests, replay evidence and timings; they have no cartridge download. Cancellation and durable request-ID deduplication use the existing job protocol. `result_routes` in capabilities are route templates, not claims that a result already exists.

`unsupported_modes` distinguishes private imported-bundle reassembly from this executable reference. The separate research CLI can rebuild admitted captured-original material after import without the external original file/source checkout. That retains original material inside the private bundle; it is not fresh IR regeneration or modification. This API release has no registered bundle upload or execution backend and reports that mode as unsupported. Whole-game byte parity alone does not establish whole-game IR coverage.

Worker ownership survives an API-server crash through a separate local supervisor. Each real worker retains a private `worker-owner.json` with an authenticated loopback control endpoint; the API never signals a PID read from disk. A restarted server probes this endpoint, reports a recovered live worker, blocks another dispatch/resume while ownership is live or unknown, and can cancel the existing writer. An unreachable owner remains fail-closed rather than being assumed dead. SIGINT/SIGTERM on the standalone server calls API shutdown and stops its authenticated owned workers. Supervisor timeouts remain enforced if the API process disappears. Stopped/unknown usage is retained for explicit engine reconciliation; cancellation does not imply resource accounting is complete. The supervisor transport source participates in runtime authority; earlier run pins are not rewritten.
